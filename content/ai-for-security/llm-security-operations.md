# 보안 관제의 LLM: 근거 기반 요약과 RAG

> **TL;DR**
>
> LLM은 보안 경보·로그·절차 문서를 정리하는 보조 도구로 사용할 수 있습니다. 근거와 추론을 구분하고, 문서별 접근 권한을 검색 단계부터 적용하며, 대응 실행은 별도의 정책으로 통제합니다.

AI 작성 해설 · 소유자 검토 전 · 출처 확인: 2026-09-10

## 어떤 업무를 맡길 수 있는가

SOC(Security Operations Center)는 보안 이벤트를 관측하고 조사·대응하는 조직과 업무를 말합니다. LLM은 여러 로그의 시간 순서를 정리하거나, 경보에서 계정·장비·시간을 추출하고, 관련 운영 절차를 찾는 데 활용할 수 있습니다. 보안 사고를 확정하는 일은 근거 확인과 업무 맥락 판단을 요구합니다.

| 업무 | 기대하는 출력 | 검증 방법 |
|---|---|---|
| 경보 요약 | 관측 사실과 관련 이벤트 ID | 원본과 대조해 누락·왜곡 확인 |
| 타임라인 구성 | 시각·행동·출처의 목록 | 시간대와 순서 검증 |
| 절차 검색 | 해당 버전의 지침과 인용 | 문서 최신성·접근 권한·내용 확인 |
| 조사 메모 초안 | 사실·가설·미확인 사항 구분 | 분석가 검토와 수정 이력 |

## RAG 파이프라인의 신뢰 경계

질문 → 요청자 권한 확인 → 허용된 문서 검색 → 관련 부분과 출처 전달 → 답변 생성 → 근거 검증 흐름을 생각할 수 있습니다. 문서와 청크에 접근 정책을 연결하고 검색 시 강제해야 합니다. 권한 없는 내용을 모델에 전달한 뒤 출력에서만 가리는 것은 충분하지 않습니다.

벡터 저장소, 캐시, 대화 기록에도 같은 데이터 경계를 적용합니다. 공유가 취소되거나 문서가 삭제되었을 때 검색 결과와 파생 데이터가 언제 갱신되는지 정합니다. 검색되는 문서 자체도 신뢰할 수 없는 내용이 포함될 수 있습니다. [OWASP RAG Security](https://cheatsheetseries.owasp.org/cheatsheets/RAG_Security_Cheat_Sheet.html)

## 사실과 가설을 분리하는 출력

다음은 원본 로그가 있다고 가정한 설명용 형식입니다. 실제 사건 판정 결과가 아닙니다.

| 구분 | 출력 예 |
|---|---|
| 관측 사실 | 이벤트 E17: 09:14 로그인 실패 3회, E18: 09:16 로그인 성공 |
| 가설 | 사용자의 입력 실수 또는 추가 확인이 필요한 로그인일 수 있음 |
| 미확인 사항 | 사용자 확인과 해당 기기의 등록 상태 |
| 출처 | E17·E18 원본 기록과 적용한 절차 문서 버전 |

“새 지역이므로 계정 침해 확정”처럼 관측에서 결론으로 건너뛰지 않게 해야 합니다. 출처 링크가 있다는 것만으로 내용이 뒷받침되는 것도 아닙니다. 인용한 기록이 실제로 주장을 지지하는지 검증합니다.

## 도구 사용과 대응 권한

로그와 티켓 본문은 분석할 데이터이며 운영 지시가 아닙니다. LLM 출력이 도구 호출 인자가 되면 도구 서버에서 요청자의 권한, 허용 대상, 인자 형식과 범위를 다시 검증합니다. 문서 요약에 필요한 읽기 권한과 계정 비활성화 권한은 분리합니다.

영향이 큰 작업에는 구체적인 대상·변경 내용·근거를 검토할 수 있는 승인 절차와 실행 이력, 복구 방법을 둡니다. 프롬프트에 금지 문구를 넣는 것만으로 도구 권한 통제를 대신할 수 없습니다. [OWASP LLM Prompt Injection Prevention](https://cheatsheetseries.owasp.org/cheatsheets/LLM_Prompt_Injection_Prevention_Cheat_Sheet.html)

## 어떻게 평가할 것인가

동일한 검토 사례에서 요약 전후 시간을 비교하고, 사실 오류·핵심 사실 누락·근거 없는 주장·권한 밖 정보 노출을 별도로 집계합니다. 답변을 유보해야 하는 자료 부족 사례도 포함합니다. 사람이 LLM의 결론에 끌려가는지 살피고, 절약된 시간만으로 품질을 판단하지 않습니다.

모델, 프롬프트, 검색기, 인덱스가 바뀌면 동일한 평가 사례를 다시 확인합니다. 원본 증거와 모델이 생성한 해설은 저장과 표시에서 구분해야 합니다.

## 검색 평가와 답변 평가 분리

먼저 권한 있는 정답 근거가 상위 k개 검색 결과에 들어오는지 평가합니다. 다음으로 그 근거를 제공했을 때 답변이 정확하고 핵심 사실을 빠뜨리지 않는지 확인합니다. 검색 누락을 생성 모델의 문제로만 보거나, 출처가 존재한다는 이유로 답변을 정확하다고 판단하지 않습니다.

## 구조화 출력과 판단 유보

타임라인을 생성한다면 event_id, observed_at, fact, hypothesis 같은 필드의 타입과 필수 여부를 검증합니다. 스키마에 맞는 문자열이어도 원본에 없는 사건을 만들 수 있으므로 사실성 검증은 남습니다. 원본 누락·시간 불일치·접근 불가 상황에서는 부족한 근거와 후속 확인 대상을 표시합니다.

유보율은 낮을수록 무조건 좋은 지표가 아닙니다. 근거 부족 사례에서의 적절한 유보와 답할 수 있는 사례에서의 불필요한 유보를 나누어 평가합니다.
