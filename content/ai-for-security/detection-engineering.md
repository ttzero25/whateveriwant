# 탐지 엔지니어링: 가설·데이터·규칙·모델의 수명

> **TL;DR**
>
> 탐지 엔지니어링은 무엇을 관측하면 어떤 위험을 의심할지 가설을 세우고, 필요한 데이터·검증·운영 절차를 유지하는 일입니다. 규칙과 ML 모두 관리할 탐지 자산입니다.

AI 작성 해설 · 소유자 검토 전 · 출처 확인: 2026-09-10

## 탐지 가설에서 시작하기

“평소와 다른 로그인”보다 “허용된 근무 맥락으로 설명되지 않는 새 기기의 접근을 검토한다”처럼 관측과 판단 조건을 명확히 합니다. 필요한 로그가 없거나 해당 필드의 의미가 불명확하면 모델부터 만들기 어렵습니다.

| 탐지 명세 | 기록할 내용 |
|---|---|
| 보호 목표·가설 | 어떤 자산과 실패를 다루는가? |
| 데이터 계약 | 필드·출처·지연·수집 중단의 의미 |
| 판단 로직 | 규칙·모델·시간 구간·임계값 |
| 검증 사례 | 발견해야 할 사례와 정상 예외 |
| 운영 절차 | 담당자·검토·복구·폐기 조건 |

## 규칙과 모델의 결합

명확한 금지 정책은 규칙으로 적용하고 모델은 검토 순위를 보조할 수 있습니다. 반대로 모델이 만든 후보를 자산 중요도와 운영 일정으로 보정할 수도 있습니다. 결합 방식이 달라지면 전체 파이프라인의 오탐·미탐도 달라지므로 최종 경보에서 평가합니다.

## 관측 범위와 탐지 범위

MITRE ATT&CK는 관측된 적대 행위를 조직하는 지식 기반입니다. 공통 언어로 탐지 가설을 정리하는 데 활용할 수 있지만 기법 ID를 연결했다는 사실이 탐지 능력의 검증은 아닙니다. 필요한 데이터가 실제로 들어오는지와 대표 사례를 발견하는지 확인해야 합니다. [MITRE ATT&CK](https://attack.mitre.org/)

## 변경과 폐기

서비스 배포 후 이벤트 스키마가 바뀌면 탐지 조건이 조용히 실패할 수 있습니다. 데이터 품질 알림, 버전, 회귀 사례를 함께 관리합니다. 중복·무용 경보는 이유를 기록해 조정하고, 탐지를 비활성화할 때 생기는 공백과 대체 관측을 검토합니다.

## 예시와 확인 질문
