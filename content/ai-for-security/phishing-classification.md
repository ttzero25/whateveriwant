# 피싱 분류 사례: 데이터에서 경보 검토까지

> **TL;DR**
>
> 피싱 분류는 본문 모델 하나로 끝나지 않습니다. 라벨·중복·시간 분할·임계값·검토 절차를 연결해 어떤 메일을 누구에게 검토하도록 보낼지 설계해야 합니다.

AI 작성 해설 · 소유자 검토 전 · 출처 확인: 2026-09-10

## 사례의 범위

다음은 실제 메일을 전송하거나 실제 성능을 측정한 결과가 아닌 설계용 가상 사례입니다. 합성 메일과 사용 권한을 확인한 비민감 데이터로 분류 파이프라인을 평가한다고 가정합니다. 목표는 자동 삭제가 아니라 검토 우선순위 제공입니다.

## 데이터를 준비하기

확인된 피싱·정상·미확인 라벨을 구분하고 판정 시점과 출처를 남깁니다. 동일한 템플릿과 사건에서 나온 유사 메일은 그룹으로 묶어 학습·평가 사이의 중복을 줄입니다. 미래에 수집할 메일을 가정해 시간 경계도 적용합니다.

특징에는 당시 이용 가능한 본문 표현과 승인된 메타데이터만 사용합니다. 조사 완료 후의 티켓 심각도를 입력으로 넣으면 미래 정보 누출이 됩니다. 외부 링크를 따라가거나 첨부파일을 실행할 필요 없이 승인된 정적 데이터 범위에서 평가할 수 있습니다.

## 기준 모델과 비교

단순 규칙과 텍스트 특징을 사용한 선형 모델을 기준으로 두고, 복잡한 모델이 정밀도·재현율·지연에서 무엇을 개선하는지 봅니다. 클래스 가중치나 재표집은 학습 분할 안에서 적용합니다. 평가셋은 운영에서 예상하는 비율과 사건 경계를 유지해야 합니다. [imbalanced-learn: Common pitfalls](https://imbalanced-learn.org/stable/common_pitfalls.html)

## 가상 결과 읽기

| 구분 | 가정한 건수 |
|---|---|
| 실제 피싱 / 정상 | 100 / 9,900 |
| TP / FN | 80 / 20 |
| FP / TN | 120 / 9,780 |

이 경우 정밀도는 80/200=40%, 재현율은 80/100=80%, 오탐률은 120/9,900≈1.21%입니다. 200건을 검토해 80건의 실제 피싱을 찾는 구성입니다. 검토 가능량이 100건이라면 임계값이나 순위를 다시 검증해야 하며, 위 숫자를 그대로 절반으로 나눌 수는 없습니다.

## 운영과 사람의 피드백

원본 참조, 모델 버전, 점수와 검토 사유를 보여 주고 분석가가 정정할 수 있게 합니다. 상위 경보만 검토한 라벨은 전체 메일의 대표 표본이 아니므로 별도의 표본 검토를 유지합니다. 새 언어·부서·메일 형식별 성능과 유보율도 확인합니다.
