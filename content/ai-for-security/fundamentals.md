# AI for Security: 보안 업무에 AI를 적용하는 법

> **TL;DR**
>
> 보안에서 AI는 이벤트를 분류하고, 이상 징후를 찾아 검토 순서를 정하며, 근거를 요약하는 데 활용할 수 있습니다. 모델의 점수와 실제 사고 판정, 대응 권한은 별도로 설계해야 합니다.

AI 작성 해설 · 소유자 검토 전 · 출처 확인: 2026-09-10

## AI for Security와 Security for AI

AI for Security는 보안 문제를 푸는 데 AI를 사용하는 것입니다. Security for AI는 모델·데이터·추론 서비스 자체를 보호하는 것입니다. 보안 로그를 분석하는 LLM 서비스라면 두 관점이 모두 필요합니다. 탐지 성능이 좋아도 서비스가 비공개 로그를 노출하면 보안 목표를 만족하지 못합니다.

| 관점 | 질문 | 예시 |
|---|---|---|
| AI for Security | 어떤 보안 업무를 개선하는가? | 피싱 의심 메일 분류, 경보 중복 묶기 |
| Security for AI | AI 구성 요소를 어떻게 보호하는가? | 데이터 접근 통제, 모델 무결성, 도구 권한 제한 |

이 컬렉션은 방어 업무의 설계와 평가를 다루며, 마지막 글에서 AI 시스템 자체의 보호까지 연결합니다.

## 업무에 맞는 방법 선택

| 방법 | 잘 맞는 일 | 필요한 전제 | 한계 |
|---|---|---|---|
| 규칙 | 명확한 정책 위반 확인 | 조건과 정책이 명확함 | 알려진 조건 밖의 변화는 놓칠 수 있음 |
| 지도학습 | 과거 판정에 따른 분류·순위화 | 신뢰할 수 있는 라벨 | 과거에 없던 환경으로의 일반화가 어려움 |
| 이상 탐지 | 평소와 다른 행동의 검토 후보 생성 | 비교할 기준과 맥락 | 드문 행동이 반드시 악성은 아님 |
| LLM | 로그·문서 요약과 정보 추출 | 검증할 근거와 출력 형식 | 사실 누락·환각·지시 오염 가능성 |

처음부터 가장 복잡한 모델을 고를 필요는 없습니다. 같은 평가 데이터에서 기존 규칙, 간단한 모델, 새 모델을 비교해야 개선의 원인을 알 수 있습니다. 기존 AI 문서의 [분류](../ai/logistic-regression.md)와 [군집화](../ai/clustering.md)를 먼저 읽어도 좋습니다.

## 관측에서 대응까지의 흐름

이벤트 수집 → 정규화·특징 생성 → 모델 점수 → 경보 묶기·우선순위 → 분석가 검토 → 대응 및 피드백 순서로 생각할 수 있습니다. 모델은 이 흐름의 한 구성 요소입니다. 수집이 끊기거나 판정이 늦게 들어오면 모델 성능만 측정해서는 문제를 찾기 어렵습니다.

예를 들어 의심 로그인 탐지의 출력이 위험 점수라면, 그 점수를 경보로 만들 임계값과 경보를 검토할 담당자를 정해야 합니다. 계정 차단은 정상 사용자를 막을 수 있으므로 필요한 근거·권한·승인·복구 조건을 별도로 정의합니다.

## 성공 기준을 먼저 쓰기

목표는 “AI 도입”보다 “같은 분석 인력으로 더 많은 실제 사고를 검토한다”처럼 측정 가능해야 합니다. 다음 항목을 함께 정합니다.

- 대상과 단위: 이메일 한 건, 로그인 세션, 사용자 하루 중 무엇을 판단하는가?
- 실패 비용: 오탐의 검토 시간과 미탐의 피해를 어떻게 평가하는가?
- 비교 기준: 기존 규칙이나 수동 절차보다 무엇이 좋아져야 하는가?
- 운영 경계: 어떤 출력은 참고만 하고 어떤 작업은 사람의 승인을 요구하는가?

AI의 설계부터 사용·평가까지 위험을 관리한다는 관점은 [NIST AI Risk Management Framework](https://www.nist.gov/itl/ai-risk-management-framework)를 참고했습니다. 위 흐름과 서비스 예시는 이 백과에서 구성한 설명입니다.

## 흔한 오해와 확인 질문

모델의 높은 점수는 조사할 이유이지 사고가 확정되었다는 뜻은 아닙니다. LLM이 근거를 유창하게 설명해도 설명의 사실성과 탐지 성능은 각각 검증해야 합니다.

확인 질문: 모델이 검토 시간을 줄였지만 중요한 사고를 더 많이 놓친다면 성공일까요? 업무 목표와 실패 비용에 따라 답해 보세요.
