# 네트워크 진단: 계층별 관측과 원인 분리

> **TL;DR**
>
> 진단은 증상에서 원인을 바로 단정하지 않고 링크·주소·경로·이름·전송·애플리케이션의 관측을 좁혀 가는 과정입니다. 한 도구의 성공과 실패가 무엇을 확인하는지 정확히 해석해야 합니다.

AI 작성 해설

## 변경 전에 증상을 기록하기

누가, 언제부터, 어느 장치·네트워크에서, 어떤 작업을 할 때 문제가 생기는지 적습니다. 모든 서비스인지 특정 이름만인지, 항상 실패하는지 큰 요청에서만 느린지 구분합니다. 최근 설정·배포 변경과 정상 비교 대상을 기록하면 추측을 줄일 수 있습니다.

## 관측 순서

| 단계 | 확인할 정보 | 다음 질문 |
|---|---|---|
| 링크 | 인터페이스 상태·연결·무선 품질 | 물리·무선 연결이 준비되었는가? |
| 주소 | IP·프리픽스·게이트웨이·임대 | 기대한 네트워크 설정인가? |
| 경로 | 선택된 라우트·다음 홉 | 어느 인터페이스로 나가는가? |
| 이름 | 리졸버·응답·TTL·캐시 | 이름 조회가 기대한 결과인가? |
| 전송·보안 | 연결 시간·재전송·TLS 오류 | 어느 교환에서 진행이 멈추는가? |
| 애플리케이션 | HTTP 상태·서버 로그·요청 ID | 도착 후 처리에서 실패했는가? |

이 표는 앞 문서의 계층 모델을 적용한 자체 진단 절차입니다. 성공한 관측을 근거로 확인 범위를 좁히되 이미 확인한 조건이 달라졌다면 다시 검토합니다.

## 도구 결과의 한계

ping은 ICMP 응답을 관측합니다. 응답이 없어도 ICMP 정책 때문에 그럴 수 있으며 웹 서비스가 반드시 중단된 것은 아닙니다. 응답이 있어도 DNS·TLS·HTTP가 정상이라는 뜻은 아닙니다. traceroute의 중간 홉 무응답도 실제 전달 실패가 아니라 응답 제한일 수 있습니다. 왕복 경로가 다를 가능성도 있습니다.

브라우저 개발자 도구의 네트워크 타이밍은 이름 조회·연결·응답 대기 등을 구분하는 데 도움이 되지만 캐시·연결 재사용 때문에 단계가 생략될 수 있습니다. 타임아웃은 원격 작업의 미완료를 확정하는 신호가 아닙니다.

## 가상 사례: 이름 조회는 되지만 HTTPS 실패

먼저 이름이 기대한 주소인지 확인하고, 해당 서비스의 연결과 TLS 오류를 분리합니다. 인증서의 이름 불일치라면 검증을 끄는 대신 서비스 이름과 인증서 구성을 확인합니다. HTTP 503이라면 네트워크 전달 이후 프록시·백엔드 상태를 로그와 연결해 조사합니다.

진단 대상은 관리 권한이 있는 환경으로 한정하고 필요한 범위의 관측을 수집합니다. 패킷과 로그에는 민감한 정보가 포함될 수 있으므로 원본 접근·보존·공유 범위를 정합니다. [보안 로깅](../security/logging-incident-response.md)
