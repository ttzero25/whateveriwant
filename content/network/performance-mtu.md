# 네트워크 성능과 MTU: RTT·대역폭·손실·큐

> **TL;DR**
>
> 대역폭은 전송할 수 있는 양, 지연은 기다리는 시간입니다. 실제 처리량은 왕복 시간·윈도·손실·큐·애플리케이션 동작에 영향을 받으며, 링크 속도 하나로 설명할 수 없습니다.

## 단위와 지표

| 지표 | 의미 |
|---|---|
| Bandwidth | 링크의 용량을 설명하는 전송률 |
| Throughput | 실제 처리한 데이터의 전송률 |
| Goodput | 재전송·프로토콜 오버헤드 등을 제외한 유용한 데이터율 |
| RTT | 요청 신호가 갔다 돌아오는 왕복 시간 |
| Jitter | 지연이 변동하는 정도 |
| Loss | 전달 중 손실; 위치·원인은 추가 관측 필요 |

100Mbps는 초당 100메가비트입니다. 바이트 기준으로는 이론상 12.5MB/s이며 실제 파일 전송률은 헤더·경쟁·처리 비용으로 더 낮을 수 있습니다.

## 대역폭·지연 곱

100Mbps, RTT 40ms인 단순화된 경로의 BDP는 100,000,000×0.04=4,000,000비트, 즉 500,000바이트입니다. 파이프를 채우려면 대략 이 정도의 데이터가 동시에 전송 중일 수 있어야 한다는 직관을 제공합니다. 실제 성능은 수신 윈도·혼잡 윈도·서버 처리 등에도 제한됩니다. [RFC 6349](https://www.rfc-editor.org/rfc/rfc6349)

## MTU와 MSS

MTU는 해당 링크나 경로가 처리할 IP 패킷 크기와 관련되고, TCP MSS는 한 세그먼트의 TCP 데이터 크기입니다. IPv4 20바이트·TCP 20바이트 헤더만 가정하면 MTU 1500에 대응하는 데이터 공간은 1460바이트입니다. 옵션·IPv6·터널 캡슐화가 있으면 같은 계산을 그대로 적용할 수 없습니다.

경로 MTU는 지나는 구간의 제약을 반영합니다. 작은 패킷은 전달되는데 큰 전송이 멈추는 경우에는 MTU와 관련 오류 전달을 살펴볼 이유가 있습니다. 그렇다고 이 증상만으로 원인을 확정할 수는 없습니다. [RFC 1191](https://www.rfc-editor.org/rfc/rfc1191)

## 큐와 애플리케이션

버퍼가 크면 짧은 급증을 흡수할 수 있지만 대기열이 길어져 지연이 커질 수 있습니다. 대역폭이 충분해도 작은 요청을 차례로 보내면 왕복 횟수에 지배됩니다. 연결 재사용·동시성·캐시를 적용할 때도 서버와 클라이언트의 자원 한도를 확인합니다. [MDN: HTTP connection management](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Connection_management_in_HTTP_1.x)
