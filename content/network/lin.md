# LIN: 스케줄로 움직이는 저비용 제어 네트워크

> **TL;DR**
>
> LIN(Local Interconnect Network)은 창문·좌석·소형 액추에이터처럼 비교적 느린 통신으로 충분한 기능에 쓰입니다. 한 commander가 통신 시점을 관리하므로 CAN의 비트 단위 중재와 동작 방식이 다릅니다.

AI 작성 해설

## 왜 CAN과 함께 쓰는가

모든 센서·액추에이터에 같은 대역폭과 비용을 배정할 필요는 없습니다. LIN은 일반적으로 단일 신호선과 공통 접지를 사용하는 저비용 서브네트워크이며, 최대 20 kbit/s 수준의 통신을 지원합니다. 단일 신호선이 전원·접지까지 모두 불필요하다는 뜻은 아닙니다. [NXP: LIN 소개](https://community.nxp.com/t5/NXP-Tech-Blog/101-Local-Interconnect-Network-LIN/ba-p/1284877)

## 헤더와 응답

commander가 헤더를 보내 통신을 시작하고, 해당 프레임에 지정된 publisher가 데이터와 체크섬으로 응답합니다. commander 자신이 publisher가 될 수도 있습니다. 어떤 프레임을 언제 보낼지는 스케줄 테이블로 관리합니다. 예전 문서의 master/slave는 commander/responder에 대응하는 용어입니다.

가상 예시로 헤더 A → 상태 응답 A → 다음 슬롯의 헤더 B → 상태 응답 B 순서를 생각할 수 있습니다. 실제 프레임 ID·주기·데이터 의미는 시스템 설계에서 정합니다.

## CAN과 비교

| 질문 | LIN | CAN |
|---|---|---|
| 통신 기회는 누가 정하는가? | commander의 스케줄 | 동시에 시작한 노드들의 중재 |
| 대표적인 설계 목적은? | 낮은 비용의 단순 제어 | 여러 제어기의 메시지 공유 |
| 지연 분석에서 무엇을 보는가? | 슬롯 간격·응답 시간 | 우선순위·버스 부하·프레임 길이 |

응답이 늦다면 센서 처리 시간뿐 아니라 다음 슬롯까지의 대기 시간을 봐야 합니다. 스케줄 방식이라고 시스템 전체의 모든 작업이 자동으로 마감 시간을 만족하는 것은 아닙니다.

## LIN에서 상위 네트워크로

LIN과 CAN을 모두 다루는 제어기는 LIN 상태를 받아 CAN 메시지로 전달할 수 있습니다. 서로 다른 전기 신호를 배선만 이어서 변환하는 방식이 아니라, 제어기 소프트웨어가 데이터 의미와 전달 주기를 연결하는 구조입니다.

네트워크 사이를 연결할 때는 값의 최신성도 중요합니다. 예컨대 센서 응답이 끊겼는데 마지막 정상 값을 계속 전달하면 수신 측이 오래된 값을 현재 상태로 오해할 수 있습니다. 이는 가상의 설계 사례입니다.
