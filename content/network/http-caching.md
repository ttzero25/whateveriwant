# HTTP와 캐시·프록시·CDN: 요청의 의미와 중간 경로

> **TL;DR**
>
> HTTP는 요청과 응답의 의미를 정의합니다. 전송 버전이 달라도 메서드·상태 코드·캐시의 의미를 구분하고, 프록시와 CDN이 어느 요청을 대신 처리하는지 이해해야 합니다.

## 메서드와 응답

| 개념 | 의미와 주의점 |
|---|---|
| GET / HEAD | 표현 조회 / 응답 헤더 조회; 상태 변경 용도로 설계하지 않음 |
| POST | 대상 자원이 정의한 처리 요청; 일반적으로 멱등성을 가정하지 않음 |
| PUT / DELETE | 정해진 의미에서 멱등인 메서드; 응답이 매번 같다는 뜻은 아님 |
| 2xx / 3xx | 성공 / 리디렉션 등의 후속 처리 |
| 4xx / 5xx | 요청 관련 문제 / 서버 측 처리 문제 |

메서드 의미를 선언해도 실제 애플리케이션이 그 의미에 맞게 구현되어야 합니다. 전송 계층 성공과 HTTP 성공, 업무 트랜잭션 성공도 서로 다릅니다. [RFC 9110: HTTP Semantics](https://datatracker.ietf.org/doc/html/rfc9110)

## 캐시의 신선도와 재검증

캐시가 신선하면 저장된 응답을 재사용할 수 있습니다. 오래된 응답은 ETag나 Last-Modified 같은 검증 정보로 서버에 변경 여부를 확인할 수 있고, 304 응답은 조건에 따라 기존 표현의 재사용을 허용합니다.

Cache-Control의 no-cache는 무조건 저장 금지가 아니라 재사용 전 검증을 요구합니다. no-store는 저장하지 않도록 요구합니다. private은 공유 캐시와 개인 캐시의 구분에 관련됩니다. Vary는 지정한 요청 헤더도 캐시의 응답 선택에 영향을 준다는 뜻입니다. [RFC 9111](https://www.rfc-editor.org/rfc/rfc9111)

## 프록시와 로드 밸런서

포워드 프록시는 클라이언트 쪽에서, 리버스 프록시는 서버 쪽에서 요청을 중개하는 관점입니다. 로드 밸런서는 여러 백엔드에 트래픽을 분산하고 상태 확인으로 대상 선택을 조정할 수 있습니다. CDN은 사용자 가까운 위치에서 캐시와 전달 기능을 제공하는 구성입니다. 모든 응답이 캐시 가능한 것은 아닙니다. [MDN: Proxy servers and tunneling](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Proxy_servers_and_tunneling)

## 사례: 로그인한 사용자의 문서

공개 이미지와 개인 문서는 캐시 정책이 달라야 합니다. 인증된 응답을 캐시할 때는 권한·캐시 키·무효화 경계를 함께 설계합니다. 원 서버에서 접근을 취소했는데 CDN에 이전 응답이 남는 상황도 고려해야 합니다. 프록시가 전달한 사용자 IP 헤더도 신뢰할 프록시 경계에서만 해석합니다.
