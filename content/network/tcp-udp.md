# TCP와 UDP: 스트림·데이터그램·흐름 제어

> **TL;DR**
>
> TCP는 순서 있는 신뢰성 있는 바이트 스트림을 제공하고 UDP는 데이터그램을 전달합니다. 메시지 경계, 재전송, 혼잡 처리와 애플리케이션 완료 확인은 각 층의 책임을 나누어 이해해야 합니다.

## 두 전송 방식의 차이

| 항목 | TCP | UDP |
|---|---|---|
| 애플리케이션이 보는 단위 | 바이트 스트림 | 데이터그램 |
| 메시지 경계 | 자체 보존하지 않음 | 데이터그램 단위 유지 |
| 순서·재전송 | 프로토콜에서 제공 | UDP 자체는 제공하지 않음 |
| 연결 상태 | 연결 수립·종료 상태 관리 | TCP 방식의 연결 수립 없음 |

TCP에 두 번 쓴 데이터가 수신 측의 두 번 읽기로 나뉘어 돌아온다고 보장할 수 없습니다. 길이 필드나 구분자처럼 애플리케이션 프로토콜의 경계가 필요합니다. UDP 기반 애플리케이션도 필요하면 신뢰성과 혼잡 제어를 별도로 구현할 수 있으며 QUIC이 그 예입니다. [TCP: RFC 9293](https://www.rfc-editor.org/rfc/rfc9293), [UDP: RFC 768](https://www.rfc-editor.org/rfc/rfc768)

## 연결과 종료

TCP의 일반적인 연결 수립은 SYN → SYN+ACK → ACK 교환으로 양쪽 상태를 맞춥니다. 각 방향의 종료를 따로 처리할 수 있으므로 보내기는 끝내고 받기는 계속할 수도 있습니다. 타임아웃, 재설정과 정상 종료는 서로 다른 결과입니다.

TCP ACK는 수신 TCP가 바이트를 받았다는 의미이지 DB 저장이나 사용자 작업의 성공을 보장하는 응답이 아닙니다. 앱의 요청 ID와 성공 응답이 필요한 이유입니다.

## 흐름 제어와 혼잡 제어

흐름 제어는 수신 측이 받을 수 있는 양을, 혼잡 제어는 네트워크 상태에 맞춰 보낼 양을 다룹니다. 수신 윈도와 혼잡 윈도는 서로 다른 제한입니다. 손실·지연·재전송과 왕복 시간이 전송 성능에 영향을 줍니다.

## 포트와 소켓

연결은 출발지·목적지 IP, 포트와 프로토콜 같은 정보로 구분합니다. 한 서버 포트가 여러 클라이언트 연결을 처리할 수 있습니다. 특정 포트가 열렸다는 사실만으로 실행 중인 서비스의 종류나 안전성을 확정하지 않습니다.
