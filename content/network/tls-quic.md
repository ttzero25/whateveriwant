# TLS·HTTP/2·QUIC·HTTP/3: 연결과 다중화

> **TL;DR**
>
> TLS는 통신을 보호하고 HTTP/2·HTTP/3는 요청을 전달하는 방식을 개선합니다. QUIC은 UDP 위에 보안과 신뢰성 있는 스트림 등을 구성하며, UDP 자체와 같은 보장 수준으로 해석하면 안 됩니다.

## TLS와 인증서

TLS는 통신 중 기밀성·무결성과 피어 인증을 제공합니다. 일반적인 웹 접속에서는 서버 인증서를 검증하며, 체인·이름·유효기간 등의 조건이 맞아야 합니다. TLS가 실제로 끝나는 지점까지가 보호 구간입니다. 프록시에서 종료하면 프록시 이후의 연결은 별도로 보호해야 합니다. [RFC 8446: TLS 1.3](https://www.rfc-editor.org/rfc/rfc8446)

## HTTP 버전과 전송

| 구성 | 핵심 특징 | 남는 문제 |
|---|---|---|
| HTTP/1.1 | 연결 재사용 등으로 여러 요청 처리 | 사용 방식에 따른 대기와 연결 수 |
| HTTP/2 | 한 연결에서 여러 스트림 다중화 | TCP 손실이 여러 스트림 전달을 지연시킬 수 있음 |
| HTTP/3 | QUIC 위에서 HTTP 의미 전달 | 경로·서버·클라이언트의 지원과 자원 한도 |

HTTP/2의 다중화는 요청마다 별도 TCP 연결이 필수라는 뜻이 아닙니다. HTTP/3는 TCP 대신 QUIC을 사용합니다. [RFC 9114](https://www.rfc-editor.org/rfc/rfc9114)

## QUIC의 스트림

QUIC은 UDP 위에서 TLS 기반 보안, 연결 관리, 신뢰성 있는 스트림과 혼잡 제어를 제공합니다. 한 스트림의 누락 데이터가 다른 독립 스트림의 순서 있는 전달을 TCP처럼 일괄 정지시키는 문제를 줄입니다. 다만 연결 수준의 혼잡과 자원 제한은 여전히 공유합니다. “손실이 다른 스트림에 아무 영향도 없다”는 뜻은 아닙니다. [RFC 9000](https://www.rfc-editor.org/rfc/rfc9000)

## 재개와 0-RTT의 한계

연결 재개는 이전 상태를 활용해 설정 비용을 줄일 수 있습니다. 일부 구성의 0-RTT 데이터는 재전송·재생 위험을 고려해야 하므로 모든 상태 변경 요청에 무조건 사용하면 안 됩니다. 빠른 연결과 안전한 업무 처리는 함께 검토할 조건입니다.
