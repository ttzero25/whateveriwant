# CPU 스케줄링과 문맥 교환

> **TL;DR**
>
> 스케줄러는 실행 가능한 작업 중 누가 CPU를 사용할지 정합니다. 응답 시간·공정성·처리량 사이의 균형이 필요하며, 문맥 교환에도 상태 저장과 복구 비용이 듭니다.

## 스케줄링이 필요한 이유

CPU에서 실행할 수 있는 흐름보다 실행 가능한 스레드가 많으면 순서를 정해야 합니다. 선점형 스케줄링은 현재 작업이 자발적으로 양보하지 않아도 타이머나 우선순위 같은 조건에 따라 다른 작업을 실행할 수 있게 합니다.

## 학습용 정책 비교

| 정책 | 아이디어 | 고려할 점 |
|---|---|---|
| FCFS | 도착한 순서대로 실행 | 긴 작업 뒤에서 짧은 작업이 대기 |
| Round robin | 일정 시간씩 번갈아 실행 | 시간 할당량과 전환 비용 |
| Priority | 우선순위에 따라 선택 | 낮은 우선순위의 기아 가능성 |

이 표는 기본 모델입니다. 실제 Linux·Windows 스케줄러를 하나의 단순 알고리즘으로 설명할 수는 없습니다. 정책·클래스·버전과 여러 코어의 배치를 함께 봅니다.

## 예시: Round robin

A와 B가 동시에 준비되어 있고 각각 CPU 4ms가 필요하다고 합시다. 시간 할당량이 2ms이고 전환 비용을 생략하면 A 2ms → B 2ms → A 2ms → B 2ms 순서가 가능합니다. 실제 시스템에서는 인터럽트·I/O·우선순위 때문에 달라집니다.

## 무엇을 측정할까?

응답 시간은 첫 반응까지, 반환 시간은 작업 도착부터 완료까지, 처리량은 단위 시간에 끝낸 작업 수입니다. 문맥 교환 때 레지스터 등 실행 상태를 저장·복구하며 캐시나 주소 변환 캐시에도 간접 비용이 생길 수 있습니다. CPU 사용률만 높다고 사용자가 빠르다고 느끼는 것은 아닙니다.

## 반환 시간과 응답 시간의 계산 예시

A·B가 동시에 도착하고 CPU를 각각 8ms·2ms 사용한다고 가정합니다. 전환 비용을 무시하고 A부터 끝내면 완료 시각은 8ms·10ms로 평균 반환 시간은 9ms입니다. B부터 끝내면 2ms·10ms로 평균은 6ms입니다. 이 예시는 작업 길이를 알고 있다는 가정에 의존합니다.

Round Robin은 긴 작업이 끝나기 전에 다른 작업에도 CPU를 주어 첫 응답을 빠르게 할 수 있습니다. 시간 조각을 너무 줄이면 문맥 교환 비용이 커집니다. 공정성·처리량·첫 응답·꼬리 지연 중 어떤 목표를 우선하는지 명시해야 합니다. [OSTEP CPU Scheduling](https://pages.cs.wisc.edu/~remzi/OSTEP/cpu-sched.pdf)
