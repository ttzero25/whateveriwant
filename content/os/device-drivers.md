# 디바이스 드라이버와 커널 모듈

> **TL;DR**
>
> 드라이버는 하드웨어의 구체적 동작을 운영체제의 일관된 인터페이스로 변환하는 커널 코드입니다. 응용 프로그램은 파일처럼 장치를 다루고, 드라이버가 그 요청을 실제 하드웨어 제어로 옮깁니다.

AI 작성 해설

## 드라이버가 메우는 간극

하드웨어마다 레지스터·프로토콜이 다릅니다. 만약 응용 프로그램이 이를 직접 다뤄야 한다면 이식성이 사라집니다. 드라이버는 장치별 세부를 감추고 공통 인터페이스(읽기·쓰기·제어)를 제공합니다. 그래서 프로그램은 디스크든 USB든 같은 방식으로 접근합니다. 시스템 콜·커널 경계는 [운영체제·커널·시스템 콜](kernel-system-calls.md)에서 다룹니다.

## "모든 것은 파일이다"

유닉스 계열은 장치를 `/dev` 아래의 특수 파일로 노출합니다. 응용 프로그램은 `open`/`read`/`write`/`ioctl`로 장치를 다루고, 커널이 이를 해당 드라이버의 함수로 연결합니다. 파일 디스크립터 개념은 [파일시스템·경로·파일 디스크립터](filesystems.md)와 이어집니다.

```c
// 응용 프로그램 관점: 장치도 파일처럼 다룬다
int fd = open("/dev/ttyUSB0", O_RDWR);   // 시리얼 장치 열기
write(fd, "AT\r", 3);                     // 드라이버가 UART 하드웨어로 전송
ioctl(fd, TIOCMGET, &status);            // 파일 모델로 표현 못하는 제어는 ioctl
close(fd);
```

## 문자 장치와 블록 장치

- **문자 장치**: 바이트 스트림으로 접근(키보드·시리얼·`/dev/random`).
- **블록 장치**: 고정 크기 블록 단위, 커널 버퍼 캐시를 거침(디스크·SSD).

블록 장치의 I/O 스케줄링·버퍼링은 [I/O·인터럽트·비동기](io-interrupts.md)와 이어집니다. 드라이버는 하드웨어가 준비됐음을 인터럽트로 통보받아 처리합니다.

## 커널 공간의 위험

드라이버는 대개 커널 공간에서 실행되어 전체 시스템 권한을 가집니다. 그래서 드라이버 버그 하나가 커널 패닉이나 권한 상승으로 직결됩니다. 신뢰할 수 없는 장치(악성 USB)도 드라이버의 파싱 취약점을 노립니다. 이 표면 축소가 [시스템 보안](../security/system-security.md)의 관심사입니다. 위험을 줄이려는 흐름으로 마이크로커널·사용자 공간 드라이버(FUSE, DPDK)가 있습니다.

```bash
# 리눅스 커널 모듈: 드라이버를 실행 중 커널에 적재/제거
lsmod                 # 적재된 모듈 목록
modinfo e1000e        # 특정 드라이버 정보
sudo modprobe <name>  # 의존성까지 해결해 적재
```

## 확인 장치와 이식성

같은 응용 코드가 여러 하드웨어에서 도는 이유는 드라이버가 차이를 흡수하기 때문입니다. 임베디드에서는 이 계층이 HAL(하드웨어 추상화 계층)로 나타납니다.
