# 동기화·뮤텍스·세마포어·교착 상태

> **TL;DR**
>
> 동기화는 공유 상태 접근과 작업 순서를 조정합니다. 뮤텍스는 상호 배제, 세마포어는 허용 수나 신호 관리에 쓰이며, 락을 사용하는 코드도 교착과 기아를 고려해야 합니다.

AI 작성 해설

## 도구별 역할

| 도구 | 일반적인 목적 |
|---|---|
| Mutex | 한 번에 하나의 실행 흐름이 임계 구역에 진입 |
| Semaphore | 카운터로 사용 가능한 자원 수 또는 이벤트 조정 |
| Condition variable | 공유 상태의 조건이 만족되기를 기다림 |
| Atomic operation | 정의된 연산을 쪼개지지 않게 수행 |

세부 소유권과 메모리 순서 보장은 API마다 다릅니다. 조건 변수는 보통 락과 함께 쓰고, 깨어난 뒤 조건을 다시 확인합니다. 하나의 원자적 변수만으로 여러 변수의 불변식이 자동으로 보호되지는 않습니다.

## 예시: 두 락의 순서가 엇갈리면

A가 락 X를 가진 채 Y를 기다리고 B가 Y를 가진 채 X를 기다린다면 서로 진행하지 못할 수 있습니다. 관련 코드 전체에서 락 획득 순서를 X → Y처럼 일관되게 정하는 방법을 검토할 수 있습니다. 예외·취소 상황에서도 해제 규칙을 지켜야 합니다.

## 교착·기아·라이브락

교착(deadlock)은 서로 필요한 자원이나 이벤트를 기다려 진행하지 못하는 상태입니다. 기아(starvation)는 특정 작업이 계속 기회를 얻지 못하는 것이고, 라이브락(livelock)은 반응과 재시도는 계속하지만 유용한 진행이 없는 것입니다.

## 헷갈리기 쉬운 점

락을 많이 추가한다고 안전성과 성능이 함께 좋아지는 것은 아닙니다. 보호할 데이터와 불변식, 모든 접근 경로를 먼저 정합니다. 긴 I/O 동안 락을 보유하면 다른 작업의 대기가 길어질 수 있습니다.

## 보호할 불변 조건과 조건 변수

잔여 수량이 음수가 되지 않으려면 수량 확인과 감소를 함께 보호해야 합니다. 각각의 읽기·쓰기가 안전해도 그 사이에 상태가 바뀌면 전체 결정은 틀릴 수 있습니다. 어떤 락이 어떤 상태를 보호하는지 문서화합니다.

조건 변수의 알림은 깨어난 순간 조건이 계속 참이라는 보장이 아닙니다. 다른 소비자가 먼저 항목을 가져갈 수 있으므로 락을 다시 가진 상태에서 조건을 재검사합니다. 교착, 계속 선택받지 못하는 기아, 활동하지만 진전이 없는 livelock도 구별해야 합니다. [OSTEP Concurrency Bugs](https://pages.cs.wisc.edu/~remzi/OSTEP/threads-bugs.pdf)
