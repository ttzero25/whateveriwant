# 키 교환과 전방향 비밀성

> **TL;DR**
>
> 키 교환은 사전에 비밀을 공유하지 않은 두 당사자가 안전한 공유 대칭키를 함께 만들어 내는 과정입니다. Diffie-Hellman이 기본 원리이며, 매 세션 임시 키를 쓰면 전방향 비밀성이 생깁니다.

AI 작성 해설

## 문제: 어떻게 첫 비밀을 나눌까

대칭키 암호는 빠르지만 두 당사자가 같은 키를 가져야 합니다([대칭키 암호](symmetric-encryption.md)). 도청되는 채널에서 어떻게 공유 키를 만들까요? Diffie-Hellman(DH)은 각자 비밀을 감춘 공개값만 주고받아, 도청자는 계산할 수 없는 공유 비밀을 양측이 독립적으로 유도하게 합니다.

## Diffie-Hellman의 직관

각자 개인 비밀 a, b를 고르고 공개값을 교환한 뒤, 상대 공개값에 자기 비밀을 결합하면 같은 공유 비밀이 나옵니다. 도청자는 공개값만 보므로 이산로그 문제 때문에 비밀을 역산할 수 없습니다.

```python
# 개념 예시(교육용 소수 사용, 실제로는 검증된 라이브러리의 X25519를 쓴다)
p, g = 23, 5                      # 공개 파라미터
a, b = 6, 15                      # 각자의 개인 비밀
A, B = pow(g, a, p), pow(g, b, p) # 공개값 교환 (A=8, B=19)
s_alice = pow(B, a, p)            # 상대 공개값에 자기 비밀 결합
s_bob   = pow(A, b, p)
assert s_alice == s_bob == 2      # 같은 공유 비밀. 도청자는 a,b를 모른다
```

실무에서는 타원곡선 기반 X25519를 쓰고, 공유 비밀은 그대로 키로 쓰지 않고 KDF로 세션 키를 유도합니다.

## 전방향 비밀성(PFS)

매 세션마다 **임시(ephemeral)** DH 키를 새로 만들면(ECDHE), 나중에 서버의 장기 개인키가 유출되어도 과거에 녹음된 트래픽은 복호화되지 않습니다. 이것이 전방향 비밀성이며, TLS 1.3이 이를 표준으로 삼는 이유입니다. TLS에서의 적용은 [TLS·HTTP/2·QUIC](../network/tls-quic.md)에서 다룹니다.

## 중간자(MITM) 문제

DH 자체는 상대가 누구인지 인증하지 않습니다. 그래서 공격자가 양쪽과 각각 키 교환을 하는 중간자 공격이 가능합니다. 이를 막으려면 키 교환에 **인증**을 결합해야 합니다: 서명이나 [PKI 인증서](pki-and-certificates.md)로 공개값의 출처를 검증합니다.
