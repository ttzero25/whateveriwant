# 분산 시스템: 복제·부분 장애·일관성

> **TL;DR**
>
> 여러 서버가 협력하는 시스템에서는 일부만 실패하거나 응답이 지연될 수 있습니다. 복제·재시도·일관성은 장애 상황에서 어떤 결과를 보장할지 정하는 설계입니다.

AI 작성 해설 · 소유자 검토 전 · 출처 확인: 2026-09-10

## 타임아웃은 실패 확정이 아니다

클라이언트가 응답을 받지 못해도 서버에서는 처리가 끝났을 수 있습니다. 요청이 도착하지 않은 경우와 완료 후 응답만 사라진 경우를 클라이언트가 구별하기 어려울 수 있습니다. 재시도는 이 불확실성을 고려해야 합니다.

| 개념 | 해결하려는 문제 | 남는 설계 질문 |
|---|---|---|
| 복제 | 한 노드의 장애와 읽기 부하 | 복제 지연과 승격 시 데이터 손실 |
| 샤딩 | 데이터를 나누어 용량·부하 분산 | 여러 샤드에 걸친 작업 |
| 멱등성 | 같은 요청의 반복에 의한 중복 효과 | 요청 식별자·결과의 보존 범위 |
| 합의 | 여러 참여자가 상태·순서에 합의 | 장애 가정과 가용성·지연 |

## 동기·비동기 복제

동기 복제는 정해진 복제 확인을 기다리는 만큼 지연과 장애의 영향을 받을 수 있습니다. 비동기 복제는 주 서버의 응답을 빠르게 할 수 있지만 장애 시 아직 전달되지 않은 변경을 잃을 수 있습니다. PostgreSQL의 복제 문서는 이런 절충과 failover 조건을 설명합니다. [PostgreSQL: Standby servers](https://www.postgresql.org/docs/current/warm-standby.html)

## 일관성과 가용성

최신 쓰기를 곧바로 읽을 수 있는지, 다른 클라이언트가 같은 순서로 관측하는지에 따라 일관성 요구가 달라집니다. 네트워크 분할 중 모든 요청에 응답하는 것과 단일 최신 상태처럼 보이게 하는 것 사이에는 절충이 생깁니다. CAP를 평상시 “셋 중 둘 고르기”로만 이해하면 조건을 놓칩니다.

## 예시: 경보 티켓 생성

동일한 사건을 재전송할 때 사건 ID를 멱등 키로 사용하고 이미 처리한 결과를 돌려주면 중복 티켓을 줄일 수 있습니다. 다만 외부 알림 발송과 DB 기록의 경계까지 자동으로 한 번만 실행되는 것은 아닙니다. 각 부수 효과의 중복과 복구를 설계해야 합니다.
