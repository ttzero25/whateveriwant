# 권한 우회: 수평·수직 권한과 정책의 일관성

> **TL;DR**
>
> 권한 우회는 허용되지 않은 자원이나 행동이 인가 정책을 제대로 거치지 않고 처리되는 문제입니다. 서버가 모든 경로에서 주체·대상·행동·조직과 현재 권한 상태를 확인해야 합니다.

## 인증 우회와 권한 우회 구분하기

인증은 누구인지 확인하고, 인가는 그 주체가 무엇을 할 수 있는지 판단합니다. 인증 우회는 신원 확인이 실패하는 문제이고, 권한 우회는 작업 허용 판단이 실패하는 문제입니다. 두 문제가 함께 나타날 수도 있습니다.

권한 상승은 원래보다 넓은 권한을 얻는 결과를 가리킵니다. 웹의 역할 정책 오류와 OS의 권한 상승은 영향을 받는 경계가 다르므로 같은 수정 방법으로 다루지 않습니다. [OWASP: Authorization](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html)

## 수평·수직·조직 경계

| 경계 | 가상 문서 서비스의 요구사항 |
|---|---|
| 수평 권한 | 같은 편집자라도 공유받지 않은 타인의 문서는 읽을 수 없음 |
| 수직 권한 | 일반 편집자는 관리자용 조직 설정을 변경할 수 없음 |
| 조직 경계 | 조직 A의 관리자는 조직 B의 자료에 자동으로 접근할 수 없음 |
| 객체·행동 | 문서를 읽을 수 있어도 수정·삭제 권한은 별도로 필요 |

IDOR·BOLA는 객체 수준 정책에 초점을 둡니다. 기능 수준 인가 실패(BFLA)는 특정 역할에 제한된 기능을 서버가 제대로 통제하지 못하는 문제입니다. 정책은 사용자 역할 하나만으로 끝나지 않습니다. [OWASP: BFLA](https://owasp.org/API-Security/editions/2023/en/0xa5-broken-function-level-authorization/)

## 정책이 빠지기 쉬운 설계 지점

같은 데이터를 다루는 상세 조회·목록·내보내기·백그라운드 작업에 서로 다른 정책 구현이 있으면 일관성이 깨질 수 있습니다. 권한 회수 후 캐시나 이미 대기 중인 작업이 어떤 정책을 따라야 하는지도 명시해야 합니다.

예컨대 문서 공유를 취소했다면 새 요청의 거절뿐 아니라 이미 생성한 다운로드 링크의 수명도 설계 대상입니다. 작업 도중 권한이 바뀌는 경우에는 작업 특성과 보호 요구에 맞춰 재검사 시점을 정합니다.

## 예방과 수정

- 공통 정책 계층에서 기본 거부를 적용하고, 서버가 보호된 작업마다 인가를 수행하게 합니다.
- 주체·조직·권한 정보는 신뢰할 수 있는 서버 측 인증 상태에서 가져옵니다.
- 입력에서 수정 가능한 필드를 명시하고 역할·소유자 같은 보호 필드는 별도 권한 절차로 관리합니다.
- 정책 오류나 의존 서비스 장애 시 검사를 생략하지 말고 작업을 거절하도록 설계합니다.

버튼 숨김, 예측하기 어려운 ID, API 게이트웨이의 로그인 검사만으로 애플리케이션의 객체별 권한이 보장되지는 않습니다.

## 허용·거절 행렬로 검증하기

격리된 테스트 데이터에 대해 주체 × 조직 × 자원 × 행동의 기대 결과를 작성합니다. 정상 기능이 유지되면서 비허용 작업은 거절되어야 합니다.

| 테스트 주체 | 대상 | 행동 | 기대 결과 |
|---|---|---|---|
| 문서 소유자 | 본인 문서 | 읽기 | 허용 |
| 읽기만 공유받은 사용자 | 공유 문서 | 수정 | 거절 |
| 다른 조직의 관리자 | 미공유 문서 | 내보내기 | 거절 |
| 공유가 회수된 사용자 | 이전 공유 문서 | 새 조회 | 거절 |

HTTP 응답 코드뿐 아니라 실제 데이터 변경·작업 생성·응답 본문에도 권한 밖의 효과가 없는지 확인합니다. 이 표는 학습용 정책 예시이며 모든 서비스의 정답은 아닙니다.
