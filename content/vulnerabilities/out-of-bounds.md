# OOB: 경계 밖 읽기와 쓰기

> **TL;DR**
>
> OOB(Out-of-bounds)는 버퍼·배열의 유효한 범위를 벗어나는 메모리 접근입니다. 읽기와 쓰기를 구분하고, 인덱스·길이·크기 계산을 실제 객체의 범위와 대조해야 합니다.

AI 작성 해설

## OOB Read와 OOB Write

| 구분 | 깨진 조건 | 가능한 영향 |
|---|---|---|
| OOB Read / 경계 밖 읽기 | 유효한 영역 밖의 값을 읽음 | 정보 노출, 잘못된 처리, 충돌 |
| OOB Write / 경계 밖 쓰기 | 유효한 영역 밖에 값을 씀 | 데이터 손상, 충돌, 프로세스 무결성 손상 |

실제 영향은 접근 위치·실행 경로·언어와 런타임에 따라 달라집니다. OOB가 있다는 사실만으로 정보 유출이나 코드 실행이 항상 가능하다고 결론 내리지는 않습니다. [CWE-125](https://cwe.mitre.org/data/definitions/125.html) · [CWE-787](https://cwe.mitre.org/data/definitions/787.html)

## 경계를 어떻게 표현하는가

길이가 N인 배열의 요소 인덱스는 0 이상 N 미만입니다. 버퍼 일부를 처리할 때는 시작 위치와 처리 길이 모두 유효해야 합니다. 빈 구간을 허용할지와 종료 위치의 포함 여부도 API 계약으로 정해야 합니다.

가상의 길이 8 배열은 요소 번호 0부터 7까지를 가집니다. “요소가 8개”와 “인덱스 8에 접근할 수 있음”은 다릅니다. 이 차이를 놓치는 한 칸의 오류를 off-by-one이라고 부릅니다.

## 원인은 접근문보다 앞에 있을 수 있다

파일에 적힌 길이를 실제 수신한 바이트 수와 대조하지 않거나, 요소 수와 바이트 수를 혼동하면 경계 검사가 잘못될 수 있습니다. 크기 계산의 정수 오버플로·부호 변환도 실제 할당 크기와 처리량을 어긋나게 만듭니다.

검사 이후 다른 작업이 버퍼를 바꾸는 경우에는 검사 결과의 유효 기간도 고려합니다. 범위 검사가 성공했어도 객체 수명이 끝났다면 별도의 [Use-after-free 문제](memory-safety.md)가 남습니다.

## 예방과 수정

- 범위를 검사하는 컨테이너·API와 메모리 안전한 언어를 우선 사용합니다.
- 길이·오프셋·요소 크기의 단위를 일치시키고 계산 범위와 실제 할당 크기를 확인합니다.
- 입력에 선언된 길이보다 실제 확보한 데이터와 객체 경계를 기준으로 처리합니다.
- 오류·취소 경로에서도 객체 소유와 수명을 유지합니다.

ASLR 같은 완화책은 잘못된 접근 자체를 고치지 않습니다. 관리되는 언어도 네이티브 라이브러리·FFI·unsafe 영역은 별도로 검토해야 합니다.

## 수정 후 확인할 조건

자체 코드의 단위 테스트에서 빈 입력, 첫 요소, 마지막 요소, 허용 최대 길이를 확인합니다. 허용 범위 밖의 요청은 접근 전에 거절되어야 하며, 거절 경로의 오류 출력도 잘못된 메모리를 읽지 않아야 합니다.

개발 빌드의 sanitizer·정적 분석과 격리된 파서 퍼징은 추가 검증 수단입니다. 도구에서 오류가 나오지 않았다는 사실만으로 모든 실행 경로가 안전하다고 증명되지는 않습니다.

## 용어와 확인 질문

이 글의 OOB는 Out-of-bounds입니다. 통신 문맥의 Out-of-band(별도 채널)와는 다른 의미입니다.
