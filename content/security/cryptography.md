# 암호학: 암호화·해시·서명과 키 관리

> **TL;DR**
>
> 암호화는 내용을 숨기고, 해시는 요약값을 만들며, MAC과 전자서명은 키를 이용해 무결성과 출처 검증을 돕습니다. 안전성은 알고리즘뿐 아니라 키·난수·nonce의 올바른 관리에 달려 있습니다.

## 도구마다 보장하는 것이 다르다

| 도구 | 키 | 주된 목적 | 한계 |
|---|---|---|---|
| 대칭키 암호 | 공유 비밀키 | 데이터를 효율적으로 암호화 | 키 전달과 보관이 필요 |
| 공개키 암호 | 공개키·개인키 | 암호화 또는 키 설정 등의 구성 요소 | 알고리즘마다 가능한 용도가 다름 |
| 암호학적 해시 | 없음 | 고정 길이 요약과 변경 비교 | 해시를 함께 바꿀 수 있다면 출처를 보증하지 못함 |
| MAC / HMAC | 공유 비밀키 | 메시지 무결성과 키 보유 여부 확인 | 같은 키를 가진 주체끼리는 작성자를 구별하지 못함 |
| 전자서명 | 개인키로 서명, 공개키로 검증 | 무결성과 서명 키 검증 | 공개키와 실제 신원의 연결을 별도로 신뢰해야 함 |

인코딩은 표현 방식을 바꿉니다. Base64는 비밀키가 없으므로 내용을 숨기지 않습니다. 서명도 내용을 숨기는 기능은 아닙니다. 전자서명이 있다고 해서 법적 의미의 부인 방지가 자동으로 성립하는 것도 아닙니다.

## 대칭키와 공개키를 함께 쓰는 이유

대칭키 방식은 큰 데이터를 처리하는 데 적합합니다. 공개키 기반 방식은 서로 비밀을 미리 공유하지 않은 주체 사이의 키 설정과 인증에 활용됩니다. 실제 보안 프로토콜은 이런 역할을 조합합니다. 공개키 알고리즘이라고 모두 암호화·서명·키 교환을 지원하는 것은 아닙니다.

## 인증된 암호화와 nonce

AEAD는 기밀성과 무결성 검증을 함께 제공합니다. 예를 들어 AES-GCM은 암호문과 인증 태그를 생성합니다. 부가 인증 데이터(AAD)는 암호화하지 않으면서 변경 여부를 확인할 데이터입니다. 복호화 시 태그 검증이 실패한 결과는 사용하지 않습니다.

nonce는 알고리즘이 요구하는 방식으로 생성·관리해야 합니다. AES-GCM에서는 같은 키로 nonce를 재사용하면 보안이 크게 훼손됩니다. 비밀일 필요와 중복되면 안 된다는 요구는 서로 다릅니다. 검증된 라이브러리와 인증된 암호화 방식을 사용하고 자체 암호 설계를 피합니다. [OWASP Cryptographic Storage](https://cheatsheetseries.owasp.org/cheatsheets/Cryptographic_Storage_Cheat_Sheet.html)

## 비밀번호는 왜 별도 방식으로 저장하는가

비밀번호는 복원할 필요 없이 입력값이 맞는지 확인하면 됩니다. Argon2id 같은 비밀번호 해시 함수는 추측 한 번에 드는 연산과 메모리 비용을 높입니다. 빠른 SHA-256만 적용하면 대량 추측 비용을 충분히 높이지 못합니다.

salt는 비밀번호마다 다른 값을 사용해 같은 비밀번호도 다른 저장값을 갖게 합니다. salt는 비밀이 아니며 해시와 함께 저장할 수 있습니다. pepper를 쓰는 경우에는 데이터베이스와 분리한 비밀로 관리합니다. 비용 파라미터는 서버 성능과 서비스 요구를 측정하고 공식 지침을 확인해 정합니다. [OWASP Password Storage](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html)

## 키의 수명과 실패 대응

키는 생성 → 보관 → 사용 → 교체 → 폐기의 수명을 갖습니다. 데이터와 키의 접근 권한을 분리하고, 소스 코드·로그에 키를 남기지 않습니다. 키 교체 시 기존 데이터를 읽는 방법과 재암호화 범위를 정해야 합니다. 키를 잃으면 데이터가 복구되지 않을 수도 있습니다.

예를 들어 문서 본문은 암호화해도 같은 서비스 계정이 모든 키와 모든 문서를 자유롭게 읽을 수 있다면 계정 침해의 영향은 여전히 큽니다. 키 관리는 [최소 권한](principles.md)과 함께 설계해야 합니다.
