# 시스템 보안: 권한·메모리·격리와 운영

> **TL;DR**
>
> 시스템 보안은 프로세스가 가진 권한과 자원 접근을 제한하고, 메모리 오류의 영향을 줄이며, 패치·감사·복구로 보호를 유지하는 일입니다. 격리와 완화 기법은 서로 다른 실패를 다룹니다.

## 프로세스와 권한 경계

프로세스는 실행 중인 프로그램이며 운영체제가 제공하는 권한으로 파일·네트워크·장치에 접근합니다. 사용자 모드와 커널 모드의 경계는 일반 프로그램이 운영체제의 모든 자원을 직접 바꾸지 못하게 합니다. 시스템 호출은 커널 기능을 요청하는 인터페이스입니다.

| 통제 | 목적 | 고려할 점 |
|---|---|---|
| 사용자·그룹·파일 권한 | 주체별 자원 접근 제한 | 서비스 계정을 나누고 불필요한 쓰기 권한 제거 |
| ACL | 더 세밀한 접근 목록 | 기본 권한과 실제 유효 권한 함께 확인 |
| Linux capabilities | 일부 특권을 기능 단위로 분리 | 필요한 기능만 부여 |
| SELinux / AppArmor | 정책으로 허용 동작 제한 | 일반 파일 권한에 추가되는 통제 |
| seccomp | 사용할 시스템 호출 제한 | 애플리케이션 동작에 맞는 정책 필요 |

서버를 일반 사용자로 실행해도 그 계정이 모든 비밀 파일을 읽을 수 있다면 피해 범위가 넓습니다. 실행 계정과 접근 가능한 자원을 함께 봐야 합니다.

## 메모리 안전성의 의미

버퍼 범위를 벗어난 접근은 객체의 유효 범위 밖 메모리를 다루는 문제입니다. Use-after-free는 수명이 끝난 객체를 사용하는 문제입니다. 두 경우 모두 프로세스의 오동작, 데이터 손상, 정보 노출 등으로 이어질 수 있습니다. 안전한 언어와 API, 소유권·수명 관리, 경계 검사가 결함 발생을 줄입니다.

## 완화 기법이 제공하는 보호

| 기법 | 역할 | 한계 |
|---|---|---|
| ASLR | 메모리 배치 예측을 어렵게 함 | 메모리 오류 자체를 제거하지 않음 |
| NX / DEP | 데이터 영역의 명령 실행을 제한 | 허용된 코드의 잘못된 동작까지 막지는 못함 |
| Stack canary | 일부 스택 손상을 탐지 | 모든 메모리 손상을 다루지 않음 |
| CFI | 허용되는 제어 흐름을 제한 | 정책 범위와 구현에 따라 보호 수준이 다름 |

예방과 완화는 함께 필요합니다. 최신 빌드 도구의 보호 옵션과 운영체제 방어를 활성화하되 결함 수정도 수행합니다. [Linux Kernel Self-Protection](https://docs.kernel.org/security/self-protection.html)

## 컨테이너와 가상 머신

일반적인 컨테이너는 호스트 커널을 공유합니다. namespaces는 자원 보기를 분리하고 cgroups는 자원 사용을 제어합니다. 가상 머신은 보통 별도 게스트 커널을 사용하며 하이퍼바이저가 경계를 제공합니다. 어느 쪽도 설정과 업데이트 없이 완전한 격리를 보장하지 않습니다.

컨테이너에서는 비특권 실행, capabilities 축소, 읽기 전용 파일시스템, 자원 한도, 필요한 볼륨만 연결하는 방식으로 권한을 줄입니다. Docker 소켓이나 광범위한 호스트 마운트는 격리를 약화시킬 수 있습니다. 이미지와 호스트의 업데이트도 관리합니다. [OWASP Docker Security](https://cheatsheetseries.owasp.org/cheatsheets/Docker_Security_Cheat_Sheet.html)

## 운영에서 유지하는 보호

패키지·이미지·서비스 목록을 관리해야 영향받는 대상을 찾을 수 있습니다. 업데이트는 호환성을 검증해 적용하고 실패 시 되돌릴 경로를 마련합니다. 감사 로그는 접근 권한과 보존 기간을 정하고 비밀번호·토큰 같은 비밀을 남기지 않습니다. 백업은 원본과 독립된 접근 통제를 적용하고 복원으로 검증합니다.

예를 들어 파일 변환 서비스는 임시 디렉터리만 쓰도록 하고 작업 시간·메모리를 제한할 수 있습니다. 변환 프로세스가 실패해도 서비스 전체와 원본 저장소의 피해가 제한되도록 설계하는 것입니다.
