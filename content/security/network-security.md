포트가 열려 있다는 사실은 애플리케이션의 사용 권한을 뜻하지 않습니다. TCP는 전달과 연결에 관한 기능을 제공하지만 그 자체로 기밀성을 제공하지 않습니다.

## TLS가 보장하는 것

TLS는 전송 중 데이터의 기밀성과 무결성을 보호하고 인증서 등으로 통신 상대를 인증하는 데 사용됩니다. 일반적인 HTTPS에서는 클라이언트가 서버 인증서를 검증합니다. mTLS에서는 서버도 클라이언트 인증서를 검증합니다.

인증서 체인, 호스트 이름, 유효기간 등을 확인하고 검증 오류를 무시하지 않습니다. 서비스에 맞는 현대적인 TLS 설정과 인증서 갱신 절차를 유지합니다. 암호화는 종단 사이에서만 적용되므로 리버스 프록시에서 TLS를 종료한다면 프록시와 백엔드 구간도 별도로 설계해야 합니다. [OWASP Transport Layer Security](https://cheatsheetseries.owasp.org/cheatsheets/Transport_Layer_Security_Cheat_Sheet.html)

HTTPS는 서버가 선의인지, 서버 안에 저장된 데이터가 안전한지, 사용자가 해당 문서를 읽어도 되는지까지 보장하지 않습니다. URL 경로와 본문이 암호화되어도 IP 주소와 트래픽 양 같은 메타데이터가 모두 숨겨지는 것은 아닙니다.

## 망 분리와 최소 연결

문서 서비스를 공개 프록시, 애플리케이션, 데이터베이스로 나눈다면 인터넷에서는 프록시에만 연결하게 하고 애플리케이션만 DB에 접근하도록 제한할 수 있습니다. 관리 접근은 별도 경로와 강한 인증으로 통제합니다.

망을 나누는 것만으로 충분하지 않습니다. 구간 사이에 필요한 통신을 정의하고 실제 정책으로 강제해야 합니다. 들어오는 연결뿐 아니라 나가는 연결도 제한하면 불필요한 외부 통신과 내부 자원 접근의 범위를 줄일 수 있습니다. [OWASP Network Segmentation](https://cheatsheetseries.owasp.org/cheatsheets/Network_Segmentation_Cheat_Sheet.html)

## 방화벽·VPN·Zero Trust

방화벽은 설정된 규칙에 따라 통신을 허용하거나 차단합니다. 상태 기반 방화벽은 연결 상태도 고려합니다. VPN은 특정 종단 사이의 통신을 터널로 보호하지만 연결한 사용자에게 모든 자원의 권한을 줘야 한다는 뜻은 아닙니다.

Zero Trust는 네트워크 위치만으로 신뢰를 부여하지 않고 주체·기기·자원·상황에 따라 접근을 검증하는 접근입니다. 내부 연결에서도 서비스 신원과 권한을 확인하고 필요 최소 범위만 허용한다는 점이 핵심입니다. [OWASP Zero Trust Architecture](https://cheatsheetseries.owasp.org/cheatsheets/Zero_Trust_Architecture_Cheat_Sheet.html)

## DNS와 탐지·가용성

DNS는 이름을 주소 등의 정보로 변환합니다. DNSSEC는 검증 가능한 DNS 데이터의 출처와 무결성을 제공하며 질의 내용을 암호화하지 않습니다. DoH·DoT는 클라이언트와 리졸버 사이의 전송을 암호화하지만 리졸버에 대한 신뢰나 목적지 서비스의 안전성까지 해결하지 않습니다. [DNSSEC: RFC 4033](https://www.rfc-editor.org/rfc/rfc4033), [DoH: RFC 8484](https://www.rfc-editor.org/rfc/rfc8484), [DoT: RFC 7858](https://www.rfc-editor.org/rfc/rfc7858)

IDS는 의심스러운 활동을 탐지하고, IPS는 배치와 정책에 따라 차단도 수행합니다. 탐지에는 오탐과 미탐이 있으며 암호화된 트래픽의 내용 가시성에도 한계가 있습니다. 네트워크 기록과 인증·애플리케이션 로그를 연결해 판단합니다. 가용성에는 요청 제한, 시간 제한, 자원 한도와 상위 네트워크의 대응도 필요합니다.
