# 보안 원칙과 위협 모델링

> **TL;DR**
>
> 보안은 보호할 자산과 신뢰 경계를 정하고, 위험의 가능성과 영향을 줄이는 설계입니다. 최소 권한·기본 거부·심층 방어는 그 설계를 구체화하는 원칙입니다.

## 무엇을 보호하는가: CIA

| 목표 | 의미 | 개인 문서 서비스의 예 |
|---|---|---|
| 기밀성 Confidentiality | 허용된 주체만 정보를 읽음 | 비공개 메모를 작성자만 열람 |
| 무결성 Integrity | 허용되지 않은 변경을 막고 알아냄 | 문서 수정 권한과 변경 이력 |
| 가용성 Availability | 필요한 때 서비스를 이용함 | 장애 복구와 복원 가능한 백업 |

목표는 서로 영향을 줍니다. 접근을 모두 차단하면 기밀성을 지키기 쉬워도 서비스의 목적을 잃습니다. 어떤 데이터에 어떤 보호가 필요한지부터 정해야 합니다.

## 자산·위협·취약점·위험

자산은 계정, 문서, 키처럼 보호할 대상입니다. 위협은 자산에 피해를 줄 수 있는 사건이나 행위이고, 취약점은 그 피해를 가능하게 하는 약점입니다. 위험은 특정 상황에서 피해가 일어날 가능성과 그 영향을 함께 판단한 것입니다. 취약점 개수만으로 위험을 비교할 수는 없습니다.

문서 서비스에서는 사용자 데이터와 관리자 계정이 자산입니다. 다른 사람의 문서를 읽는 일이 위협이고, 서버의 소유자 확인 누락이 취약점입니다. 공개 도움말과 의료 기록의 노출은 같은 결함이어도 영향이 다릅니다.

## 설계에 적용하는 원칙

| 원칙 | 설계 질문 | 예시 |
|---|---|---|
| 최소 권한 Least privilege | 이 작업에 꼭 필요한 권한인가? | 조회 서비스에는 읽기 권한만 부여 |
| 기본 거부 Deny by default | 허용 규칙이 없을 때 어떻게 되는가? | 새 API는 정책 등록 전 접근 거부 |
| 완전한 중재 Complete mediation | 매 접근에서 권한을 확인하는가? | 다운로드에도 객체별 인가 적용 |
| 심층 방어 Defense in depth | 한 통제가 실패하면 무엇이 남는가? | 인가·저장소 권한·감사를 함께 적용 |
| 공격 표면 축소 | 불필요한 진입점이 있는가? | 사용하지 않는 API와 서비스 제거 |
| 안전한 실패 | 검증에 실패해도 보호가 유지되는가? | 정책 조회 오류 시 민감 작업 거부 |

인가 원칙은 [OWASP Authorization](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html), 진입점과 신뢰 경계 분석은 [OWASP Attack Surface Analysis](https://cheatsheetseries.owasp.org/cheatsheets/Attack_Surface_Analysis_Cheat_Sheet.html)를 참고했습니다.

## 위협 모델을 만드는 순서

1. 보호할 데이터와 실패 시 피해를 적습니다.
2. 브라우저 → API → 저장소의 데이터 흐름을 그립니다.
3. 인터넷과 내부망, 사용자와 관리자처럼 신뢰가 달라지는 경계를 표시합니다.
4. 경계마다 누가 무엇을 잘못 요청하거나 변경할 수 있는지 묻습니다.
5. 예방·탐지·복구 방법과 담당자를 정하고 남은 위험을 기록합니다.

문서 공유 기능을 추가하면 수신자, 만료, 공유 취소라는 새 경계가 생깁니다. 기능이 바뀔 때 위협 모델도 갱신해야 합니다.

## 흔한 오해와 확인 질문

내부망이라는 이유만으로 요청자를 신뢰할 수는 없습니다. 암호화도 과도한 권한이나 잘못된 수신자를 해결하지 못합니다. 보안 제품의 개수보다 각 통제가 어떤 실패를 막는지 설명할 수 있어야 합니다.

확인 질문: 백업이 있어도 복원해 본 적이 없다면 가용성이 검증되었다고 말할 수 있을까요? 보호 대상과 실패 시 동작을 함께 설명해 보세요.
