# 클라우드 IAM과 비밀 관리: 서비스 신원과 수명

> **TL;DR**
>
> 클라우드에서는 사용자뿐 아니라 워크로드에도 신원과 권한이 있습니다. 자격 증명의 수명을 줄이고 자원별 접근과 비밀의 생성·교체·폐기를 함께 관리해야 합니다.

## 사용자와 워크로드의 신원

사람의 로그인 계정, 애플리케이션의 서비스 계정, 자동 배포 작업은 다른 주체입니다. 역할과 정책으로 어떤 자원에 어떤 행동을 허용할지 정합니다. 네트워크가 내부라는 이유로 IAM 검증을 생략하지 않습니다.

| 설계 질문 | 예시 |
|---|---|
| 누가 요청하는가? | 특정 배포 작업의 워크로드 신원 |
| 무엇을 할 수 있는가? | 특정 저장소의 배포물 읽기 |
| 언제·어떤 조건인가? | 허용된 실행 환경과 제한된 세션 |
| 어떻게 회수하는가? | 세션 만료와 역할·정책 변경 |

클라우드의 책임 분담은 서비스 유형에 따라 달라집니다. 관리형 서비스를 써도 고객 데이터, 권한 설정과 애플리케이션의 책임이 모두 사라지는 것은 아닙니다. [OWASP Secure Cloud Architecture](https://cheatsheetseries.owasp.org/cheatsheets/Secure_Cloud_Architecture_Cheat_Sheet.html)

## 비밀의 수명

키·토큰·비밀번호를 소스와 로그에서 분리하고 비밀 저장소에 접근하는 주체를 제한합니다. 가능하면 장기 공유 키 대신 짧은 수명의 자격 증명을 사용합니다. 교체는 새 키 발급, 소비자 갱신, 동작 검증, 이전 키 폐기의 순서를 포함합니다. 교체 실패와 서비스 연속성도 고려해야 합니다. [OWASP Secrets Management](https://cheatsheetseries.owasp.org/cheatsheets/Secrets_Management_Cheat_Sheet.html)

## 사례: 로그 요약 서비스

요약 서비스에는 허용된 로그를 읽는 권한만 부여하고 사용자 계정 변경 권한은 주지 않습니다. 검색 인덱스와 비밀 저장소의 권한도 나눕니다. 모델 제공자에게 전송되는 내용, 보존 정책과 지역 요구는 조직의 데이터 정책에 맞춰 검토합니다.

## 흔한 오해

환경 변수는 전달 방법이지 비밀 관리 전체가 아닙니다. 프로세스 덤프, 디버깅 출력, 과도한 실행 권한을 통해 노출될 수 있습니다. 저장 암호화도 해당 서비스가 모든 키와 데이터를 읽을 수 있는 과도한 권한을 해결하지 않습니다.
